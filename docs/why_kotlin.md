Why is SkyHanni written in Kotlin and not in Java?

The following text analyzes the benefits and downsides of Kotlin versus Java for developing a mod for Hypixel Skyblock using Forge 1.8.9. This includes considerations on performance, compatibility, maintainability, and ecosystem support.

# Kotlin vs Java for Forge 1.8.9 Skyblock Mod Development

Using Kotlin to develop a Minecraft Skyblock mod (Forge 1.8.9) comes with its own set of advantages and disadvantages compared to the traditional Java approach. Below is a detailed comparison across key areas:

## Performance

- **Runtime Speed:** Kotlin compiles to JVM bytecode just like Java, so there is virtually no difference in execution speed between a Kotlin mod and a Java mod. The JVM’s JIT optimizes both languages similarly, and most code will run at the same speed ([Kotlin object creation and memory management compared to Java - Stack Overflow](https://stackoverflow.com/questions/53801893/kotlin-object-creation-and-memory-management-compared-to-java#:~:text=I%20think%20you%20mean%20Kotlin,tell%20you%20about%20this%20target)). In some cases, Kotlin can even inline functions or lambdas to improve performance slightly (a benefit in certain scenarios that Java 8 lacks natively), but overall you should expect **comparable performance to Java**.

- **Memory & Overhead:** There is no significant per-object memory overhead for using Kotlin – objects and data classes have the same memory footprint and performance characteristics as in Java ([Kotlin object creation and memory management compared to Java - Stack Overflow](https://stackoverflow.com/questions/53801893/kotlin-object-creation-and-memory-management-compared-to-java#:~:text=I%20think%20you%20mean%20Kotlin,tell%20you%20about%20this%20target)). However, using Kotlin **does require bundling the Kotlin Standard Library** and runtime with your mod (since neither Minecraft nor Forge includes it by default). This adds roughly **2-3 MB** to the mod and means more classes to load into memory ([Kotlin and Minecraft Forge](https://shadowfacts.net/2016/kotlin-and-minecraft-forge/#:~:text=Additionally%2C%20Forgelin%20repackages%20the%20Kotlin,of%20Kotlin%20libraries%20multiple%20times)). In practice, this is a small overhead (it slightly increases initial load time and RAM usage), and for a typical mod it’s usually negligible. Aside from that, Kotlin’s additional runtime features (like null-safety checks) have minimal impact on performance – e.g., Kotlin may insert null-check instructions (calls to `Intrinsics`) which are very fast and only run when necessary. Overall, **CPU and memory performance is on par with Java**, with the only notable overhead being the inclusion of the Kotlin runtime library.

## Compatibility with Forge 1.8.9

- **Language Interoperability:** Kotlin is designed for 100% interoperability with Java. This means your Kotlin mod can directly use Forge’s 1.8.9 Java APIs (call methods, implement interfaces, inherit classes, etc.) and it will behave just like Java code from Forge’s perspective ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=Since%20Kotlin%20was%20created%20with,need%20a%20fat%20jar%20anyway)). Annotations like `@Mod`, `@EventHandler`, and other Forge-specific hooks can be used in Kotlin classes without issue. In short, **Kotlin integrates with the Forge API smoothly**, and you can mix Kotlin and Java in the same project if needed.

- **Mod Loader Integration:** The main compatibility consideration is providing Kotlin’s runtime to the game. Forge 1.8.9 does *not* natively include Kotlin support, so a mod written in Kotlin **must include the Kotlin standard library** (and runtime) or else it won’t run. Typically, this is done by shading (packing) the Kotlin stdlib into your mod jar, creating a “fat jar.” If you don’t do this, users would need to install a separate “Kotlin for Forge” dependency mod to supply the Kotlin library, which is not ideal in 1.8.9 ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=Read%20what%20Mqlvin%20said)). Including the library is straightforward with Gradle (using Shadow plugin or similar), but it’s an extra step compared to a pure Java mod. Once the Kotlin runtime is included, Forge will load your mod’s classes just like any other.

- **Forge 1.8.9 Limitations:** One minor limitation is that Forge 1.8.x came before built-in language adapters were common. Newer Forge versions have language adapters (like KotlinLanguageAdapter in later mods) to, for example, directly support a Kotlin `object` as the mod entry. In 1.8.9, you should ensure your `@Mod` class is a normal class (not a Kotlin `object`) so Forge can instantiate it. You can still use Kotlin singletons or companion objects for convenience, but you might need to annotate certain things with `@JvmStatic` or use top-level functions to mimic static behavior where Forge expects it. This is a small adjustment; in general, **Kotlin code works with the Forge 1.8.9 framework**, but you may need to follow Java conventions (e.g. using static initializers or fields via Kotlin’s `@JvmStatic`) in a few places due to how Forge reads mods.

- **Initial Setup:** Setting up a Forge 1.8.9 environment with Kotlin can be slightly trickier simply because it’s not the standard. Many official or community templates are in Java, and those that use Kotlin often target newer Minecraft versions. In fact, developers have noted that most tutorials or templates for Kotlin mods were for Forge 1.12+ or were outdated when trying to set up Kotlin on 1.8.9 ([Forge 1.8 with Kotlin? | Hypixel Forums](https://hypixel.net/threads/forge-1-8-with-kotlin.5012748/#:~:text=Hi%2C%20I%27ve%20been%20trying%20to,a%20mod%20like%20this%3F%20Thanks)). You may need to manually configure Gradle or seek out community-made example projects to get started. Once configured, though, day-to-day compatibility is solid.

## Maintainability (Code Readability & Long-Term Development)

- **Conciseness and Clarity:** One of Kotlin’s biggest draws is its conciseness. It dramatically **reduces boilerplate code**, which can make the mod’s source more readable and maintainable. For example, data classes automatically implement `toString()`, `equals()`, and `hashCode()`; you have properties instead of explicit getter/setter methods; and features like type inference, when-expressions, and extension functions let you express logic with fewer lines. This means a well-written Kotlin mod can be easier to understand at a glance, since you’re not wading through as much repetitive code. Especially given that Forge 1.8.9 is stuck on Java 8, you won’t have access to newer Java features like `var`, records, or improved collections – but Kotlin gives you a more modern language on the same JVM ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=It%27s%20often%20said%20that%20modern,fact%20Kotlin%20has%20null%20safety)). In short, **Kotlin offers a more expressive, modern syntax**, which can improve maintainability by making code intent clearer and files shorter.

- **Null Safety and Bug Prevention:** Kotlin’s type system enforces null-safety, meaning references are non-null by default and you have to explicitly handle nullable types. This helps avoid many NullPointerExceptions (the infamous “billion dollar mistake” of Java) ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=That%20means%20with%20Kotlin%20you,fact%20Kotlin%20has%20null%20safety)) ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=But%20for%20your%20case%20I,the%20mod%20of%20your%20dreams)). For a large mod project, this can improve reliability and save you from certain bugs – a long-term maintainability win. You’ll catch potential null issues at compile time instead of encountering random crashes at runtime, which is especially useful when dealing with Minecraft’s nullable game data (Kotlin will force you to consider nulls where they are possible).

- **Complexity and Learning Curve:** On the other hand, Kotlin is a **more complex language** than Java, with a lot of advanced features and syntactic sugar. This flexibility can be a double-edged sword. It’s easy to write concise code, but it’s also possible to write very idiomatic or “clever” Kotlin that might confuse others (or your future self). As one modder put it, Kotlin’s rich features can encourage you to “golf your code into a hard to read mess” if you’re not disciplined ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=Kotlin%20has%20A%20LOT%20of,the%20basics%20in%20my%20opinion)). Maintaining a Kotlin codebase might be challenging for team members who aren’t familiar with the language’s idioms. By contrast, Java’s verbosity can actually aid clarity – the code tends to be straightforward and easier for a beginner to follow, since there’s less magic happening. In fact, community members often suggest that those new to modding stick to Java because Kotlin’s powerful features can be overwhelming without solid Java experience ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=Java%2C%20I%27d%20stick%20with%20Java)).

- **Long-Term Considerations:** If you are comfortable with Kotlin, you may find you can develop and **iterate faster with less boilerplate**, which is great for long-term development. Refactoring and adding new features can be easier when the language gives you higher-level constructs (for example, writing DSL-like code or using functional patterns). Just be mindful to keep the codebase clean – using Kotlin doesn’t automatically guarantee maintainability; it still requires good coding practices. Overall, Kotlin can improve maintainability by providing a more succinct and expressive code style, but only as long as the developers (present and future) are on board with understanding that style. If you anticipate that others will work on the mod or that you’ll need to collaborate with the broader modding community, remember that **Java is more universally understood** in this space.

## Ecosystem Support (Tools, Libraries, Documentation)

- **Community and Documentation:** The Forge modding community – especially for Minecraft 1.8.9 – predominantly uses Java. This means the **vast majority of tutorials, documentation, sample code, and forums/Q&A are in Java**, not Kotlin. If you choose Kotlin, you’ll often need to translate Java examples into Kotlin on your own. For instance, official Forge docs and older 1.8.9 modding guides make no mention of Kotlin. Community support for Kotlin is growing, but it’s still a niche in the Minecraft modding world. One developer noted that rewriting a mod in Java kept them “in sync” with the community and made it easier to get help, since most others use Java ([Should I just switch to Java? - General Discussion - Forge Forums](https://forums.minecraftforge.net/topic/60496-should-i-just-switch-to-java/#:~:text=Thanks%20for%20the%20Kotlin%20suggestion,whenever%20I%20have%20a%20doubt)). You should be prepared for the possibility that when you run into an issue, the answers you find online will be Java-centric. That said, Kotlin code can generally be understood by an experienced Java developer with a bit of effort, but it’s an extra cognitive step.

- **IDE and Build Tools:** On the tooling front, **Kotlin is very well supported**. JetBrains’ IntelliJ IDEA (a popular IDE for Minecraft mod development) has first-class Kotlin support, including debugging, autocomplete, and decompiling Java to Kotlin on the fly. Gradle, which is used in Forge’s build system, can be easily configured to compile Kotlin sources (either via the Kotlin plugin or Kotlin DSL). So, from a pure tooling perspective, you won’t be lacking – you can set up your development environment to be just as comfortable as for Java. Additionally, mixing Kotlin and Java in one project is possible, so you could write most of the mod in Kotlin but still use an occasional Java class or library if needed. **Unit testing and other tooling** works the same as on Java, since it all runs on the JVM. In short, your development workflow (code editing, building, testing) will remain smooth with Kotlin.

- **Libraries and APIs:** Kotlin can directly use any existing Java library, which means all Minecraft/Forge libraries or utilities are available. You don’t lose access to any part of the ecosystem – e.g., if there’s a Java library for Skyblock-specific features or a Forge helper library, you can include it and call it from Kotlin without issue. There are also a few Kotlin-specific libraries in the modding scene (for newer versions of Forge, mods like **Forgelin** or **Kotlin for Forge** provide language adapters and utilities for Kotlin). For Minecraft 1.8.9, those options are more limited because Kotlin wasn’t widely used back then, but you might find community projects or templates that demonstrate Kotlin usage. The examples of Kotlin-based mods (like *Warlords+* or *TapActions* for Hypixel Skyblock as referenced on forums) show that people have successfully used Kotlin in this ecosystem ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=If%20you%20want%20to%20use,8%20and%20use%20Kotlin)). Still, **expect to blaze your own trail** a bit: you’ll be using general Kotlin knowledge plus Forge’s Java docs, rather than specialized Kotlin-for-Forge documentation, simply because the latter is scarce for 1.8.9.

- **Community Tools:** One thing to note is that some **community tools and modding plugins assume Java**. For example, bytecode manipulation tools or ForgeGradle plugins are written with Java in mind, but since your mod ultimately produces standard bytecode, these usually still work fine. If you use mixins or coremod techniques (more common in newer mod loaders or versions than in 1.8.9 Forge), you might need to ensure the mixin definitions account for Kotlin class names (which can include synthetic elements like `$` in class names for inner classes or companions). This is an edge case, but worth keeping in mind. In general, **the modding ecosystem won’t actively hinder you from using Kotlin**, but it won’t explicitly cater to it either, given Java is the norm.

## Potential Issues and Pitfalls

- **Bundling the Kotlin Runtime:** The most immediate pitfall when using Kotlin is forgetting to include the Kotlin runtime in your mod distribution. If you compile your mod and give someone the jar *without* the Kotlin stdlib, it will **crash on startup** because Forge/Minecraft can’t find Kotlin classes (e.g. you might see `NoClassDefFoundError: kotlin/JvmInternal/Intrinsics` at runtime) ([minecraft forge - Bundling Kotlin runtime with my jar in grade - Stack Overflow](https://stackoverflow.com/questions/76809195/bundling-kotlin-runtime-with-my-jar-in-grade#:~:text=java,dispatchRenderLast%28ForgeHooksC)). This error is essentially the game telling you “I don’t know what Kotlin is.” To avoid this, you must properly shade or include the Kotlin standard libraries in the mod jar. This typically involves a Gradle Shadow plugin configuration or using a fat jar. It’s an extra build step that Java mods don’t require, so new Kotlin modders sometimes trip up here. The fix is straightforward, but **it’s a critical setup step** not to overlook.

- **Mod Size and Conflicts:** Including the Kotlin library will make your mod jar larger (a few MB). If you are the only one doing this, it’s just a bit of extra size. However, if a player has *multiple Kotlin-based mods* in their 1.8.9 client, there’s a possibility of class duplication or version conflicts. For instance, if two mods bundle different versions of the Kotlin stdlib, it could lead to inconsistent behavior or one mod crashing. In practice, since 1.8.9 Kotlin mods are rare, this might not happen often. But this issue was seen in the past with Scala (Forge once included Scala for mods, which turned into a headache when mods required different Scala versions) ([Include the Kotlin runtime in Forge - Suggestions](https://forums.minecraftforge.net/topic/73452-include-the-kotlin-runtime-in-forge/#:~:text=Include%20the%20Kotlin%20runtime%20in,work%20on%20the%20newest)). The Forge community’s solution in later versions was to create a single Kotlin loader mod (like Forgelin or Kotlin for Forge) so that the Kotlin runtime is loaded once and shared ([Kotlin and Minecraft Forge](https://shadowfacts.net/2016/kotlin-and-minecraft-forge/#:~:text=Additionally%2C%20Forgelin%20repackages%20the%20Kotlin,of%20Kotlin%20libraries%20multiple%20times)). On 1.8.9, you likely don’t have a widely adopted shared Kotlin loader, so just be aware of the potential for **duplicate library classes**. Keeping your Kotlin version consistent with others (should there be any) and watching mod load logs for warnings can help. Generally it’s not a common problem in the 1.8.9 scene, but it’s a consideration Java mods don’t need to worry about.

- **Language Quirks with Forge:** Most of the time, Kotlin works with Forge without special effort, but there are a few quirks to note. Forge and Minecraft rely on certain conventions (like static fields, or public no-argument constructors for some things, etc.). Kotlin can do all these, but you might need to explicitly tell Kotlin to generate them. For example, if Forge needs a static field or method (perhaps for an @EventHandler in an `@Mod.EventBusSubscriber` in newer versions, or a network channel instance), you should use `companion object` with `@JvmStatic` members so Forge sees a true static. If you use a top-level function in Kotlin for an event handler, Forge’s classpath scanning might not pick it up unless it's in a class with the annotation. These are edge cases and usually solvable by structuring your code in a Java-like way where needed. Another example: if you use Kotlin `object` for singletons, Forge might treat it just like any other class with a INSTANCE field – usually fine, but be cautious if something expects a certain class name or constructor. In summary, **Kotlin may require a bit of extra attention to Forge's expectations**, but there are no showstopper issues documented. It’s more about understanding how Kotlin compiles things and ensuring Forge can interact with the result.

- **Debugging and Stack Traces:** When something goes wrong, stack traces in a Kotlin mod might look a little different from pure Java. You’ll see Kotlin library functions (like those in `kotlin.jvm.internal` for null checks or other intrinsics) in the trace. This isn’t a huge problem, but it can be slightly harder for someone unfamiliar with Kotlin to read. For example, a null pointer exception in Kotlin might be reported as an `IllegalStateException` thrown by `Intrinsics.checkNotNull` with a custom message, rather than a direct NPE at a line of your code. As the developer, you can still trace it to your code, but it’s something to get used to. Additionally, if you ever decompile your mod (or if others do), the decompiled Java code may look a bit odd due to Kotlin’s compiled form (e.g. extra null checks, synthetic classes for things like lambdas or coroutines). These are more minor inconveniences than serious issues, but they differentiate the experience from standard Java modding.

- **Community Support Gaps:** As touched on earlier, a Kotlin modder is somewhat off the beaten path in Forge 1.8.9. If you hit a very specific issue (say, a bug with how an older Kotlin version interacts with something, or anGradle Kotlin DSL problem in your build), you might not find many Forge-specific answers readily. You may end up solving some problems yourself or asking in general Kotlin communities. This isn’t a technical flaw in Kotlin or Forge per se, but it’s a reality that can pose a challenge during development. In contrast, a weird issue in a Java mod is more likely to have been seen by someone else in the past decade of Forge modding. So, be prepared for a bit of self-reliance when venturing into Kotlin mod development on an older Minecraft version.

## Conclusion

In summary, **using Kotlin for a Forge 1.8.9 Skyblock mod is entirely feasible** and brings modern language conveniences to your project. You’ll benefit from more concise code, null-safety, and a generally enjoyable development experience if you prefer Kotlin’s style. Performance-wise, you won’t be giving up anything significant by choosing Kotlin over Java – the mod will run just as fast in almost all cases ([Kotlin object creation and memory management compared to Java - Stack Overflow](https://stackoverflow.com/questions/53801893/kotlin-object-creation-and-memory-management-compared-to-java#:~:text=I%20think%20you%20mean%20Kotlin,tell%20you%20about%20this%20target)). The biggest trade-offs come in the form of **extra overhead and learning curve**: you need to bundle the Kotlin runtime and navigate a Java-centric ecosystem. Compatibility with Forge 1.8.9 is good, but not plug-and-play – expect a bit more initial setup (finding the right build script tweaks, ensuring the mod loads Kotlin classes properly, etc.) and possibly educating yourself through sparse documentation. Maintainability can be improved with Kotlin’s features, but only if you and any collaborators write clean Kotlin; otherwise, it can backfire with hard-to-read code ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=Kotlin%20has%20A%20LOT%20of,the%20basics%20in%20my%20opinion)). Ecosystem support for Kotlin is growing, yet for an older Forge version you might often be on your own, translating Java solutions to Kotlin.

**Ultimately, the choice comes down to your comfort and priorities**. If you value writing in a modern language and are willing to handle the extra setup, Kotlin can make your mod development more pleasant and your codebase more robust (especially given Java 8’s limitations) ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=It%27s%20often%20said%20that%20modern,fact%20Kotlin%20has%20null%20safety)). If you prefer to minimize friction and tap into the full reservoir of community knowledge, sticking with Java might save you some headache, since it’s the “path of least resistance” in the Minecraft modding scene ([Should I just switch to Java? - General Discussion - Forge Forums](https://forums.minecraftforge.net/topic/60496-should-i-just-switch-to-java/#:~:text=Thanks%20for%20the%20Kotlin%20suggestion,whenever%20I%20have%20a%20doubt)). Many developers experienced with both languages would pick Kotlin for themselves any day due to its conveniences, but they acknowledge that for a beginner or for maximizing compatibility, Java is a perfectly valid choice as well ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=But%20does%20that%20mean%20you,the%20mod%20of%20your%20dreams)) ([Java or Kotlin For Skyblock ? | Hypixel Forums](https://hypixel.net/threads/java-or-kotlin-for-skyblock.5701581/#:~:text=Java%2C%20I%27d%20stick%20with%20Java)).
